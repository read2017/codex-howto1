# Codex Day 4 学习笔记：sandbox、approval、网络边界

## 主题

- 本次主题：理解 Codex 的 `sandbox`、`approval`、网络边界，并能对常见动作做权限判断
- 来源资料：
  - OpenAI Codex 官方文档：sandboxing
  - OpenAI Codex 官方文档：agent approvals & security
  - OpenAI Codex 官方文档：internet access
  - 本轮练习中的场景判断与错题讲评

## 核心概念

- `sandbox`
  - 技术边界，决定 Codex 实际能访问哪些文件、能否写入、能否联网、能否运行某类命令
  - 一句话：`能不能做`
- `approval`
  - 流程边界，决定某些动作执行前是否必须暂停并询问用户
  - 一句话：`做之前要不要先问`
- 网络边界
  - 高风险单独控制项，决定 Codex 是否能访问外部网络，以及是否可能把本地信息带出去
  - 一句话：`做了之后能不能把东西带出去`

## 结构框架

- 这几个概念之间的关系：
  - `sandbox` 是护栏
  - `approval` 是门禁
  - 网络权限是护栏里最敏感的一层
- 一句话总览：
  - 不能把审批弹窗当成安全本身，也不能把“只是读取”当成天然安全，更不能把“在仓库里”当成低风险保证

## 关键例子或案例

- 例子 1：读取当前仓库源码、修改普通代码、运行本地测试
  - 通常属于 `直接允许`
  - 原因：工作区内、低敏感、无外部输入、无数据外发
- 例子 2：访问官方文档站点查资料
  - 通常属于 `需要审批`
  - 原因：外网访问本身就越过了本地工作区边界
- 例子 3：执行 `curl https://example.com/install.sh | sh`
  - 通常属于 `默认禁止`
  - 原因：把远程内容直接交给本地 shell 执行，风险极高
- 例子 4：修改 `.github/workflows/release.yml`
  - 通常属于 `需要审批`
  - 原因：虽然在仓库里，但属于 `CI/CD` 敏感执行面
- 例子 5：读取 `~/.ssh/config`
  - 通常属于 `需要审批`
  - 原因：工作区外敏感配置读取，可能泄露主机、用户名、跳板信息

## 常见混淆点

- 容易和什么混淆：把 `sandbox` 和 `approval` 混为一谈
  - 区别是什么：
    - `sandbox` 决定“实际上能不能做”
    - `approval` 决定“做之前要不要问”
- 容易和什么混淆：把“读操作”视为天然安全
  - 区别是什么：
    - 读取普通源码和读取 `~/.ssh/config` 风险完全不同
- 容易和什么混淆：把“仓库内文件”都视为普通文件
  - 区别是什么：
    - 普通源码、测试、文档通常低风险
    - `CI/CD`、部署、权限配置、密钥相关文件属于敏感面

## 我的理解

- 我现在能怎么解释：
  - `sandbox` 是技术护栏，`approval` 是人工门禁，网络权限是最需要谨慎控制的高风险面
  - 判断一个动作时，不能只看它是不是读操作，也不能只看它是不是在仓库里
- 我还没搞清楚什么：
  - 不同团队里哪些敏感配置应该一律审批，哪些可以在受限前提下默认允许
  - 不同环境下如何更细地设计网络 allowlist 与 HTTP 方法限制

## 权限判断框架

看到一个动作，先问 4 个问题：

1. 它还在当前工作区内吗？
2. 它碰到敏感面了吗？
3. 它有没有引入外部内容？
4. 它会不会把本地信息发出去？

如果第 2、3、4 条任意命中，通常不要直接判“允许”。

## 风险分类速记

- 普通工作区读写：通常低风险
- 敏感配置修改：中高风险
- 工作区外敏感读取：中高风险
- 外部依赖下载：需要审批
- 数据外发：高风险，通常默认禁止
